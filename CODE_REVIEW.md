## 1. Баги и ошибки

### 🔴 Критические (безопасность / работоспособность)

#### B1. WebSocket-терминал LXC не аутентифицирован — удалённый root-доступ без авторизации
**Файл:** `backend/app/api/proxmox/vms.py:2951` (`terminal_websocket_fixed`)

Эндпоинт `/proxmox/ws/terminal/{server_id}/{node}/{vmid}` не принимает токен и не проверяет ни пользователя, ни сессию, ни владение контейнером. Внутри он сам получает auth-ticket по сохранённому паролю сервера Proxmox и открывает интерактивный root-shell в контейнере.

Фронтенд тоже подключается без токена:
```
/proxmox/ws/terminal/${sid}/${data.node}/${vid}   // ConsolePage.tsx:157 — токена нет
```

**Последствие:** любой, кто имеет сетевой доступ к панели, может открыть root-консоль в любом LXC-контейнере без логина. Это полный обход RBAC.

**Что сделать:** добавить аутентификацию по `?token=<jwt>` (как сделано в `/ws/tasks` в `main.py:298`), декодировать токен, проверить сессию через `SecurityService.validate_session` и право `vms.console` + `require_vm_access(server_id, vmid)`.

#### B2. VNC WebSocket-прокси не проверяет пользователя
**Файл:** `backend/app/api/proxmox/vms.py:1993` (`vnc_websocket_proxy`)

Эндпоинт `/proxmox/ws/vnc/...` принимает `auth_ticket`/`vncticket` query-параметрами и не валидирует JWT-сессию панели. Это слабее, чем B1 (нужно владеть тикетом, который выдаёт авторизованный REST-эндпоинт), но эндпоинт всё равно не привязан к пользователю и не проверяет `require_vm_access`. Тикеты попадают в URL → могут осесть в логах прокси/браузера.

**Что сделать:** так же, как B1 — аутентифицировать соединение JWT-токеном и проверять доступ к VM, не полагаясь только на ticket в URL.

#### B3. SSH-fallback удаления ноды кластера упадёт с `TypeError`
**Файл:** `backend/app/proxmox/mixins/cluster.py:289`

```python
ssh = SSHClient(hostname=self.host, username='root', password=getattr(self, '_password', None))
```
Конструктор `SSHClient.__init__` (`backend/app/ssh_client.py:24`) **не имеет параметра `password`** — только `key_path`. Любой вызов этого fallback бросит `TypeError: __init__() got an unexpected keyword argument 'password'`, то есть удаление ноды по SSH никогда не работает (а паролевая аутентификация в `SSHClient` вообще не реализована — только ключи/agent).

**Что сделать:** либо добавить поддержку `password` в `SSHClient`, либо убрать неподдерживаемый аргумент и реализовать паролевую auth через `client.connect(..., password=...)`.

### 🟠 Высокие

#### B4. Небезопасные значения по умолчанию в конфиге
**Файл:** `backend/app/config.py:37,54`

- `SECRET_KEY = "your-secret-key-here"` по умолчанию. На старте `main.py:118` есть проверка и аварийный выход — хорошо. Но `ADMIN_PASSWORD = "admin123"` по умолчанию **без** аналогичной проверки: при незаданной переменной создаётся админ с предсказуемым паролем.
- `CORS_ORIGINS = "*"` по умолчанию (`config.py:51`). Логика в `main.py:224` корректно отключает credentials при `*`, но дефолт всё равно открытый.

**Что сделать:** при `DEBUG=false` падать/предупреждать, если `ADMIN_PASSWORD` дефолтный; требовать явный список CORS-origin в проде.

#### B5. JWT хранится в `localStorage` — уязвимо к XSS
**Файл:** `frontend/src/lib/api-client.ts:15,24`, `stores/auth-store.ts:20`

Токен лежит в `localStorage`, а CSP разрешает `'unsafe-inline' 'unsafe-eval'` для скриптов (`main.py:249`). При любой XSS токен утекает. CSP с `unsafe-eval`/`unsafe-inline` фактически отключает защиту от инъекций скриптов.

**Что сделать:** перейти на httpOnly-cookie для токена (или хотя бы убрать `unsafe-eval`, использовать nonce для inline-скриптов). Для текущей схемы — минимизировать поверхность XSS.

#### B6. `datetime.utcnow()` — наивное время на колонках с timezone
**Файл:** `backend/app/api/dashboard.py:42,91`

Проект ввёл `utcnow()` helper (`config.py:92`) именно чтобы избежать наивных datetime на `timezone=True` колонках, но в dashboard всё ещё используется `datetime.utcnow()`. Сравнение naive/aware datetime в Postgres даёт смещение/ошибки в статистике за 24ч.

**Что сделать:** заменить на `from ..config import utcnow` и `utcnow()`.

#### B7. Глобальный exception handler может проглатывать `HTTPException`
**Файл:** `backend/app/main.py:261-272`

Зарегистрированы оба: handler на `Exception` и на `HTTPException`. В Starlette это работает, но `@app.exception_handler(Exception)` перехватывает всё, и порядок/диспетчеризация хрупкие — стоит убедиться (тестом), что 4xx не превращаются в 500 «Internal server error».

### 🟡 Средние

#### B8. Возможные утечки DB-сессий в фоновых воркерах
**Файл:** `backend/app/workers/monitoring_worker.py`

10 вызовов `SessionLocal()` против 8 `db.close()`. Большинство обёрнуты в try/finally, но число не сходится — нужно проверить, что каждая открытая сессия закрывается (особенно ветки с ранним `return` внутри try до создания finally). Незакрытые сессии исчерпывают пул соединений Postgres.

#### B9. `decrypt_value` ловит `Exception` и возвращает шифротекст как «plaintext»
**Файл:** `backend/app/crypto.py:59`

```python
except (InvalidToken, Exception):
    return value
```
Перехват широкого `Exception` означает, что при битом `FERNET_KEY` (например, ключ сменили) зашифрованные пароли молча вернутся как нечитаемый шифротекст, и панель будет пытаться логиниться в Proxmox мусором — без явной ошибки. Тяжело диагностировать.

**Что сделать:** ловить только `InvalidToken`; логировать прочие исключения.

#### B10. Кэш SSH-соединений — общий на класс, потокобезопасность
**Файл:** `backend/app/ssh_client.py:21-22`

`_connections`/`_connection_times` — словари уровня класса, доступ из `ThreadPoolExecutor` (10 воркеров) без блокировок. Возможны гонки при одновременном `_cleanup_connection`/`_cache_connection` (KeyError на `del`). `cleanup_ssh_connections` определён, но, судя по `main.py`, не запускается в lifespan — кэш чистится только лениво.

#### B11. `WarningPolicy` для неизвестных SSH-ключей
**Файл:** `backend/app/ssh_client.py:86`

`set_missing_host_key_policy(WarningPolicy())` принимает любой новый host key (только предупреждение) — уязвимо к MITM. Для управления инфраструктурой стоит `RejectPolicy` + управляемый known_hosts, либо явная фиксация fingerprint сервера в БД.

#### B12. Перебор VMID до 999999 в памяти
**Файл:** `backend/app/api/proxmox/_helpers.py:115-126`

Fallback грузит все vmid в set и линейно ищет свободный до 999999 — приемлемо сейчас, но это O(n) запрос + цикл на каждый вызов; при росте — узкое место. Это fallback, так что низкий приоритет.

### 🟢 Низкие / гигиена

- **B13.** Мусорные скрипты в репозитории: `fix_crud.py`, `test_new_operations.py` (корень), `backend/refactor_proxmox.py`, `backend/refactor_vms.py`, `backend/replace_imports.py` — одноразовые рефактор-скрипты, их стоит удалить из VCS.
- **B14.** Рассинхрон версий: `VERSION`/README говорят 1.5.1, fallback в `config.py:19` — `1.7.0`. Привести к единому источнику истины.
- **B15.** `import` внутри функций (`requests`, `websockets`, `init_admin`, RBAC-движок) разбросаны по горячим путям — мелкий оверхед и затруднённый анализ зависимостей. Лучше выносить наверх модуля.
- **B16.** `print(msg, end="")` как sink loguru (`main.py:43`) вместо `sys.stderr` — лог уходит в stdout, мешается с данными в некоторых деплоях.

## 2. Рекомендации по оптимизации

### Backend
1. **Пул соединений к Proxmox.** `_get_proxmox_client` создаёт новый `ProxmoxClient` на каждый запрос. Стоит кэшировать клиентов per-server (с TTL/проверкой живости), как уже сделано для SSH.
2. **Асинхронность.** Тяжёлые синхронные вызовы (`requests`, `proxmoxer`, SSH) блокируют event loop в части эндпоинтов. VNC/term уже на httpx/websockets — стоит и REST-вызовы к Proxmox перевести на async или прятать в `run_in_executor` (как `async_check_server_status`).
3. **N+1 в синхронизации.** В `sync_vm_cache` и dashboard убедиться, что нет поштучных запросов в циклах по VM; использовать `joinedload`/bulk-загрузку (частично уже применяется для IPAM).
4. **Кэш метрик/статусов.** RRD и статусы серверов опрашиваются часто — централизованный кэш с инвалидацией (Redis или in-memory с TTL) снизит нагрузку на Proxmox API.
5. **Индексы БД.** Проверить индексы на горячих фильтрах: `VMInstance(server_id, vmid, deleted_at)`, `IPAMAllocation(status)`, логи по `created_at`. Это самые частые WHERE.
6. **Закрытие сессий через контекст-менеджер.** Заменить ручные `SessionLocal()/close()` в воркерах на `with SessionLocal() as db:` чтобы исключить B8.

### Frontend
7. **Code-splitting уже есть** (lazy import xterm/noVNC) — хорошо. Стоит проверить размер основного бандла и вынести тяжёлые страницы в отдельные чанки.
8. **React Query / SWR.** Судя по обилию `use-*` хуков и polling-эндпоинтов (`main.py:92` фильтрует GET-polling), стоит убедиться, что используется дедупликация запросов и разумный `staleTime`, а не голый `setInterval`.
9. **WebSocket вместо polling.** Для unread-count уведомлений и списка серверов — перейти на уже существующий WS-канал вместо периодических GET (их специально прячут из логов, что намекает на шум).

### Инфраструктура
10. **Pin зависимостей фронтенда** и регулярный `npm audit` / `pip-audit`. `paramiko 3.4.1`, `cryptography>=41` — проверить на свежие CVE.
11. **Healthcheck** уже есть (`/health`) — добавить readiness отдельно от liveness (готовность миграций/воркеров).

## 3. Идеи для новых фич

### Управление и автоматизация
- **2FA / TOTP** для входа — логично дополняет уже развитую систему сессий, brute-force защиты и блокировок IP.
- **API-ключи для пользователей** — программный доступ к панели (для CI/CD, terraform-провайдера) с ограниченными правами.
- **Шаблоны/«flavor» VM** — преднастроенные конфигурации (S/M/L: cores/RAM/disk) для самообслуживания пользователей в стиле облачных провайдеров.
- **Расписания** (cron) для авто-старта/стопа VM, отложенных снапшотов — APScheduler уже в стеке.
- **Терраформ/Ansible экспорт** конфигурации серверов и VM как код.

### Мониторинг и алертинг
- **Пороговые алерты** (CPU/RAM/disk > X% в течение N мин) с уже подключёнными каналами (In-App/Email/Telegram).
- **Webhook-канал** уведомлений (Slack/Discord/Mattermost) в дополнение к Telegram.
- **История метрик** с долгим хранением (сейчас RRD от Proxmox) — собственная TSDB-витрина и дашборды.
- **Отчёты о ёмкости** (capacity planning): прогноз исчерпания диска/IPAM-сети.

### Сеть и хранилище
- **Управление бэкапами/restore через UI** с привязкой к расписанию и retention-политиками (бэкап-шедулер уже есть — расширить UI/политики).
- **Firewall-правила Proxmox** через панель (датацентр/нода/VM уровни).
- **Управление storage** (пулы, использование, ISO/template upload через UI).

### UX / администрирование
- **Аудит-журнал с экспортом** (CSV/PDF) — у вас уже есть LogsPage и audit в RBAC, добавить выгрузку и фильтр по пользователю/действию.
- **Bulk-теги и поиск** по VM/контейнерам (по владельцу, тегу, ноде).
- **Тёмная/светлая тема** — судя по `theme-store.ts` уже частично есть; довести до полноты.
- **Самообслуживание пользователей**: квоты (max VM/CPU/RAM на пользователя) — естественное продолжение модели владения VM и RBAC.
